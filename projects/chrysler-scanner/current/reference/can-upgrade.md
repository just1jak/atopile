# CAN upgrade scope

Decision, 2026-10-27: finish the present CCD/PCI/SCI revision and document CAN for a later hardware revision. No CAN transceiver or switching has been added to the present board.

CAN and the legacy interfaces can coexist in one scan tool. The restriction is the present circuit's shared connector wiring, not an inability of scan tools to support both. The ESP32 in ESP32-PICO-V3-02 has one Classic CAN/TWAI controller; it needs an external physical-layer transceiver. It does not support CAN FD. See the [ESP32-specific Espressif TWAI documentation](https://docs.espressif.com/projects/esp-idf/en/v5.4.4/esp32/api-reference/peripherals/can.html). Documentation for other ESP32 variants must not be used to infer this controller's capabilities.

OBD pins 6/14 presently connect to SCI/programming circuitry. Adding a transceiver in parallel would expose it to those operating modes and can load or drive the wrong interface. The next revision needs a connector-side, default-disconnected, break-before-make selector for BOTH conductors. Select a relay or switch whose working voltage, fault voltage, off leakage, capacitance and contact/current ratings cover the actual programming and vehicle fault envelope. Preserve the existing safety permit and enforce hardware mutual exclusion among CAN, SCI and programming. A firmware mode variable alone is insufficient. Verify startup, brownout, unpowered operation and stuck-control faults.

A candidate transceiver family is [TI TCAN1042HGV](https://www.ti.com/product/TCAN1042HGV): 5 V main supply, a separate 3.3 V I/O supply, standby, high-impedance unpowered bus behavior and ±70 V bus fault protection. This is a family-level option, not a released BOM selection. The fault rating does not authorize connecting live CAN traffic to legacy programming paths. Select an exact ordering code and review its complete electrical limits with the selector, protection and supply circuit.

Reserve two GPIOs through the ESP32 GPIO matrix for CAN TX/RX, plus an independently fail-safe mode/standby control. GPIO5 and input-only GPIO39 are possible allocation candidates because they are currently unused, but GPIO5 is a boot strap: the next design must verify boot levels and attached loads before assigning it. Do not use GPIO13, which remains the dedicated supervised health heartbeat. Recheck every package pin against the ESP32-PICO-V3-02 datasheet and the actual native netlist when implementing the new revision.

Place the CAN protection and selector near the connector; use appropriate low-capacitance bus protection with a short return. Route CANH/CANL together with short stubs. A diagnostic tool normally joins an already terminated vehicle network, so do not fit a permanent 120 Ω load across OBD 6/14. Provide optional, default-off bench termination if needed. Review bus loading, common-mode range, protection clamp voltage, hot plugging, EMC and connector fault behavior as a complete circuit.

Firmware work includes a mutually exclusive transport state machine, listen-only discovery, bus-off recovery, timestamps, filtering and ISO-TP/ISO 15765 support where required. Preserve logging throughput and SD arbitration. CAN FD would additionally require an external CAN FD controller (and a suitable transceiver), a new SPI/interrupt allocation and another throughput review; an FD-capable transceiver alone does not upgrade the present ESP32 controller.

Before release of that revision: native schematic/PCB checks, independent pin and mode-interlock review, actual fault/transition tests, CAN waveform and termination measurements, load/throughput tests, and a refreshed fabrication/assembly package. None of those CAN implementation gates is claimed complete by this document.
